## Locked Decisions

### 1. Transition Alias Policy For `production_date`

Decision:

- Canonical write field is `assigned_production_day`.
- `assigned_production_day` is a `YYYY-MM-DD` date string.
- During transition, backend may also write `production_date` as an alias with the same `YYYY-MM-DD` value if existing frontend/admin code still reads it.
- `assigned_production_day` is the source of truth.
- `production_date` is deprecated read compatibility only.

Implementation rule for later:

- Never write a weekday label such as `Tuesday` or `Friday` to `assigned_production_day`.
- If a weekday label is needed for display, derive it in the UI from `assigned_production_day`.

### 2. Customer-Safe Schedule Failure Error Copy

Decision:

Use this exact customer-safe error message when checkout scheduling cannot be confirmed:

> We're having trouble confirming your delivery window right now. Please try again in a few minutes or contact NuVira support.

Implementation rule for later:

- If a valid schedule cannot be calculated, fail closed.
- Do not create a PaymentIntent.
- Do not create an Order.
- Do not create an operational fulfillment record.

### 3. `final_schedule_source` Enum Values

Allowed values:

- `backend_cadence`
- `admin_override`
- `route_review_approval`
- `subscription_renewal`
- `legacy_migration`
- `unknown`

Implementation rule for later:

- One-time checkout schedules generated by the backend cadence use `backend_cadence`.
- Route review approval schedules use `route_review_approval`.
- Subscription renewal schedules use `subscription_renewal`.
- Admin-edited schedules use `admin_override`.
- Migrated historical schedules use `legacy_migration`.
- `unknown` is allowed only for legacy or recovery records where source cannot be established.

### 4. Schedule-Options Mode Shape

Decision:

- `calculateNuViraFulfillmentSchedule/entry.ts` remains the backend source-of-truth function.
- If checkout needs selectable schedule options, add or read an options mode from this function later.
- Do not create a separate competing schedule function.

Backend response shape:

```json
{
  "ok": true,
  "timezone": "America/Chicago",
  "generated_at": "ISO string",
  "options": [
    {
      "option_id": "string",
      "production_date": "YYYY-MM-DD",
      "delivery_date": "YYYY-MM-DD",
      "delivery_window_label": "Wednesday 5 PM - 8 PM",
      "delivery_window_start": "ISO string",
      "delivery_window_end": "ISO string",
      "cutoff_window_label": "string",
      "final_schedule_source": "backend_cadence",
      "scheduling_reason": "string",
      "is_default": true
    }
  ]
}
```

Allowed `delivery_window_label` values for current cadence:

- `Wednesday 5 PM - 8 PM`
- `Saturday 12 PM - 3 PM`

Implementation rules for later:

- `generated_at` is the backend timestamp when options are produced.
- `option_id` must be stable enough for a single checkout attempt and must encode or reference the generated option.
- The default option should be the earliest valid delivery option.
- All option timestamps must use `America/Chicago` semantics.
- Frontend may display these options but must not treat them as final until backend validation.

### 5. Backend Validation Response For Stale Frontend Option

Decision:

If the frontend submits a stale or invalid delivery option and the backend chooses to reject instead of override, return:

```json
{
  "ok": false,
  "error_code": "STALE_DELIVERY_SELECTION",
  "message": "That delivery window is no longer available. Please select a new delivery window.",
  "latest_options": []
}
```

Implementation rules for later:

- `latest_options` uses the same option shape defined above.
- Backend may either reject stale selection with this response or override with the current valid schedule.
- If overriding, the response/order metadata must clearly reflect the backend-selected final schedule.
- Stale frontend schedule values must never be persisted as canonical Order schedule fields.
